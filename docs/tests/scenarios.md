# Тестовые сценарии

Владелец: Участник 1. Источники: `docs/SCORING.md` (7 тестовых компаний), `docs/STATE_MACHINE.md`, `docs/api/openapi.yaml` (v0.2.0), `docs/MVP.md`.
Сценарии написаны так, чтобы их можно было и пройти руками в интерфейсе, и автоматизировать в `tests/e2e/` (pytest + httpx).

## Как читать

- Все пути API указаны без префикса `/api/v1`. Все учётки: пароль `Demo12345!`.
- «Ожидаемые статусы» это цепочка, которую должен показать `GET /applications/{id}/history`. Между статусами заявку двигает воркер, поэтому тест не ждёт фиксированное время, а опрашивает заявку до нужного статуса (таймаут 30 с по умолчанию, в демо-режиме цель из `MVP.md`: не более 10 с).
- Числа в офферах рассчитаны независимым расчётом по `SCORING.md` (ключевая ставка 14,0%: значение подтверждено решением Банка России от 23.10.2026; в `SCORING.md` указана дата предыдущего решения, 11.09.2026, с той же ставкой, и её обновление идёт отдельными правками `MVP.md` и `SCORING.md`). Допуск для `monthly_payment_rub`: ±5 ₽ (способ округления в контракте не задан). Если меняется ключевая ставка в `config.yaml`, ставки и суммы в сценариях 1–4 и 7 нужно пересчитать (формулы в разделе «Расчёт»).
- Названия экранов и кнопок в шагах UI приведены по интерфейсу после PR #8: разделы «Мои заявки», «Компания», «Новая заявка» (подбор продукта это первый шаг мастера).
- Тексты статусов берутся из API (`status_title`, `status_description`); тест проверяет, что они непустые, а точные формулировки сверяет только там, где они закреплены в `SCORING.md` (`reason_messages`, `explanation` оффера).

### TC-01. Компания 1: автоматический оффер и выдача (группа A)

| Поле | Значение |
|---|---|
| Предусловия | `client1@demo.local`, компания «Ромашка Логистик», ИНН 0000001011; seed загружен; моки без сбоев (`MOCK_BKI_FAIL_FIRST_N=0`) |
| Шаги в UI | Войти → «Компания» (данные предзаполнены) → «Сверить с реестром» → «Сведения совпадают с реестром» → «Новая заявка»: первый шаг подбора, цель «Закупки, зарплаты, текущие расходы» → рекомендация «Оборотный кредит» → 2 000 000 ₽, 12 мес, финансовые данные из таблицы, загрузить финансовую отчётность → проверить и отправить → на странице заявки наблюдать смену статусов → «Принять» → на экране «Подпишите документы» ввести 6-значный код, показанный на экране |
| Шаги через API | `POST /auth/login` → `POST /applications` (черновик) → `POST /applications/{id}/documents` (FINANCIAL_STATEMENT) → `POST /applications/{id}/submit` с `Idempotency-Key: tc01-submit-0001` → опрос `GET /applications/{id}` до `OFFER` → `GET /applications/{id}/offer` → `POST /applications/{id}/offer/accept` с `If-Match: "<version>"` → опрос до `SIGNING` → `POST /applications/{id}/sign` (с кодом подтверждения, если он добавлен в контракт; уточнить у Участника 2) |
| Ожидаемые статусы | `DRAFT → SUBMITTED → DATA_CHECK → ENRICHMENT → SCORING → OFFER → ACCEPTED → SIGNING → DISBURSED` |
| Ожидаемый результат | Группа A, балл 95. Оффер `ORIGINAL`: 2 000 000 ₽, 12 мес, ставка 18,0%, платёж ≈ 183 360 ₽. `next_action`: на `OFFER` равен `REVIEW_OFFER`, на `ACCEPTED` равен `NONE`, на `SIGNING` равен `SIGN`. Финальный экран с пометкой «Имитация: реальной интеграции с подписанием и выдачей нет». Блок «На что повлияло решение»: до двух факторов в плюс и до двух в минус простыми фразами, без баллов и весов (проверяется после добавления `decision_highlights` в контракт). Неверный код подтверждения не принимается: статус остаётся `SIGNING`, повторный ввод возможен |
| Проверка через API | После `submit` ответ 202 со статусом `SUBMITTED`. В `history` у переходов `actor_type`: `CLIENT` (подача), `SYSTEM` (проверки, оффер), `CLIENT` (принятие), `SYSTEM` (ACCEPTED → SIGNING), `CLIENT` (подпись). После `accept` ответ содержит статус `ACCEPTED`, а не `SIGNING` |
| Критерий прохождения | Цепочка статусов точно совпадает, условия оффера совпадают с ожидаемыми, итог `DISBURSED`, повторный `sign` даёт 409 `INVALID_TRANSITION` |

## Негативные сценарии

Для всех негативных сценариев формат ошибки: `{"error": {"code": "...", "message": "...", "details": [...]}}`; проверяется HTTP-статус и `code`.

| ID | Название | Предусловия и шаги | Ожидаемый результат |
|---|---|---|---|
| NEG-01 | Невалидный ИНН: формат | `PUT /company` с ИНН из 9 цифр или с буквами | 422 `VALIDATION_ERROR`, в `details` поле `inn` |
| NEG-02 | Невалидный ИНН: контрольная сумма (только через API: в интерфейсе регистрации нет) | Новый пользователь (`POST /auth/register`), `PUT /company` с ИНН `0000001012` (формат верен, контрольная цифра нет), форма `OOO`, заявка `EXPRESS` на 300 000 ₽, 6 мес, финансовые данные заданы → `submit` | Цепочка `SUBMITTED → DATA_CHECK → REJECTED`, `reason_codes = ["INVALID_INN"]`, текст «ИНН указан неверно, проверьте номер» |
| NEG-03 | Подача без обязательного поля | `POST /applications` только с `product_code`, `amount_rub`, `term_months` (без выручки, прибыли, платежей) → `submit` | 422 `VALIDATION_ERROR`, `details` содержит поля `revenue_12m_rub`, `net_profit_12m_rub`, `existing_monthly_payments_rub`; статус остаётся `DRAFT` |
| NEG-04 | Сумма или срок вне диапазона продукта | `EXPRESS`, 2 000 000 ₽ (максимум 1 500 000) или срок 24 мес (максимум 12); также `WORKING_CAPITAL` на 100 000 ₽ (минимум 300 000) | 422 `VALIDATION_ERROR` при `PATCH` или `submit`, `details` указывает поле |

## Сквозной тест (для `tests/e2e/`)

Автоматизируются TC-01 … TC-07 и NEG-01 … NEG-18. Сценарии RES-01 и RES-02 добавляются в автоматический прогон только при наличии управления моками из теста или отдельного compose-профиля. Сценарий RES-07 добавляется после решения Участника 2 о шаге сверки с реестром. Порядок: сначала `reset-demo`, затем сценарии. **Ограничение входа:** лимит `LOGIN_RATE_LIMIT_PER_MINUTE` в бэкенде считается и по IP, и по аккаунту и учитывает все попытки, включая успешные, поэтому тесты логинятся один раз на учётку и переиспользуют токен, а на время прогона лимит поднимается (например, `LOGIN_RATE_LIMIT_PER_MINUTE=1000`). NEG-20 запускается отдельным прогоном со значением 10. Ожидание статуса: цикл опроса `GET /applications/{id}` с интервалом 0,5 с и общим таймаутом 30 с, без `sleep` на фиксированное время.
