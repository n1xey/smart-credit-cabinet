# Скоринг и кредитное решение (явно принятое упрощение)

Владелец: Участник 4 (реализация), Участник 1 (параметры и тестовые сценарии).
Принцип из кейса: **скоринг и кредитное решение — разные модули.** Скоринг превращает данные в оценку риска и объяснимый разбор по факторам. Решение (матрица правил) использует оценку, продукт, сумму, срок и проверки, чтобы выбрать исход. Все пороги ниже синтетические и лежат в конфиге (`backend/app/scoring/config.yaml`), а не в коде.

## Входные данные

| Поле | Источник |
|---|---|
| `business_age_months`, `okved`, `declared_address` | профиль клиента + ЕГРЮЛ (мок) |
| `revenue_12m_rub`, `net_profit_12m_rub`, `existing_monthly_payments_rub` | вводит клиент в заявке |
| `registry_status` (`ACTIVE` / `LIQUIDATING` / `LIQUIDATED`), `registry_flags` | ЕГРЮЛ/ФНС (мок) |
| `bki_score` (0–1000), `bki_overdue_active_days`, `bki_overdue_closed_12m_count` | БКИ (мок) |
| `product`, `amount_rub`, `term_months` | заявка |

## Шаг 0. Стоп-факторы (до скоринга)

| Код | Условие | Исход |
|---|---|---|
| `REGISTRY_NOT_ACTIVE` | статус в реестре не `ACTIVE` | отказ |
| `BKI_OVERDUE_90` | действующая просрочка по БКИ более 90 дней | отказ |
| `NEGATIVE_REVENUE` | выручка 12 мес ≤ 0 | отказ |
| `AGE_TOO_LOW` | возраст бизнеса менее 3 мес | отказ |
| `PRODUCT_NOT_AVAILABLE` | `EXPRESS` при возрасте бизнеса менее 12 мес | отказ с предложением другого продукта (`COUNTER_OFFER` если условия подходят иначе — в MVP: отказ с причиной) |

## Шаг 1. Скоринговая карта (0–100, чем выше, тем лучше)

| Фактор | Условие | Баллы |
|---|---|---|
| Возраст бизнеса (макс. 15) | < 6 мес / 6–12 / 12–36 / ≥ 36 | 0 / 4 / 10 / 15 |
| Покрытие запроса выручкой, `revenue_12m / amount` (макс. 20) | < 2 / 2–5 / 5–10 / ≥ 10 | 0 / 8 / 15 / 20 |
| Рентабельность, `net_profit / revenue` (макс. 15) | < 0 / 0–5% / 5–15% / ≥ 15% | 0 / 5 / 10 / 15 |
| Долговая нагрузка, `existing_payments / (revenue/12)` (макс. 15) | > 40% / 25–40% / 10–25% / < 10% | 0 / 4 / 10 / 15 |
| Кредитная история `bki_score` (макс. 20) | < 450 / 450–599 / 600–749 / ≥ 750 | 0 / 5 / 12 / 20 |
| Статус и флаги ФНС (макс. 5) | флаги риска (массовый адрес, недостоверность) / нет флагов | 0 / 5 |
| Отраслевой риск по ОКВЭД (макс. 10) | высокий / средний / низкий | 2 / 6 / 10 |
| **Штраф:** активная просрочка БКИ > 30 дней | | −15 |
| **Штраф:** закрытые просрочки за 12 мес | за каждую, до −10 | −5 |

Итог ограничивается диапазоном 0–100. Каждое начисление и штраф сохраняются как строка разбора `{factor, value, points, max_points, comment}` — это и есть «объяснимость» для оператора.

**Группы риска:** A ≥ 75, B 60–74, C 45–59, D 30–44, E < 30.

Справочник отраслевого риска (пример): низкий — 62 (оптовая и розничная торговля продуктами), 69 (юридические услуги), 62.01 (разработка ПО); средний — 47, 49, 56; высокий — 41, 43 (строительство), 55, 90 (развлечения). Файл `okved_risk.yaml`.

**Границы диапазонов:** левая граница включительно, правая исключительно (например, возраст ровно 12 месяцев попадает в диапазон «12–36», а ровно 36 месяцев в «≥ 36»). Знаки «≥» и «>» читаются буквально. Демо-данные подбираются так, чтобы не лежать на границах.

## Ставки и ключевая ставка
Организаторы просили реалистичные условия с учётом ключевой ставки Банка России. Ставка продукта вычисляется, а не задаётся числом:
```
final_rate = KEY_RATE_PERCENT + product_spread + grade_premium
```
- `KEY_RATE_PERCENT` хранится в `config.yaml`: **14,0** (решение Банка России от 11.09.2026). Перед релизом проверить актуальное значение и при изменении обновить одну константу и дату в README.
- `product_spread`: `WORKING_CAPITAL` +4,0 п.п., `EQUIPMENT` +2,5 п.п., `EXPRESS` +7,0 п.п.
- `grade_premium`: A: 0, B: +2,0, C: +4,0 п.п. (определяет оператор для D).
- При ключевой 14,0 базовые ставки равны 18,0 / 16,5 / 21,0%, поэтому ожидаемые исходы тестовых компаний не меняются.

## Шаг 2. Кредитное решение (матрица)

Расчёт доступной суммы (упрощение):
```
monthly_capacity = 0.5 * (net_profit_12m / 12) - existing_monthly_payments
max_amount_by_capacity = PV(final_rate, term, monthly_capacity)   # аннуитет; final_rate = базовая + надбавка группы
```
Если `monthly_capacity <= 0`, `max_amount_by_capacity = 0`.

| Группа | Правило | Исход | Ставка |
|---|---|---|---|
| A | сумма ≤ `max_amount_by_capacity` и ≤ автолимит продукта | `OFFER` на запрошенных условиях | базовая |
| A | сумма ≤ `max_amount_by_capacity`, но > автолимита | `MANUAL_REVIEW` | базовая |
| A | сумма > `max_amount_by_capacity` | `COUNTER_OFFER` с суммой = `max_amount_by_capacity` (округление вниз до 10 000 ₽) | базовая |
| B | как A | как A | базовая + 2,0 п.п. |
| C | сумма ≤ `max_amount_by_capacity` и ≤ автолимита | `OFFER` | базовая + 4,0 п.п. |
| C | иначе | `COUNTER_OFFER` (сумма = min(лимиты), срок не более 24 мес для оборотного) либо `MANUAL_REVIEW`, если `max_amount_by_capacity` < минимума продукта | базовая + 4,0 п.п. |
| D | всегда | `MANUAL_REVIEW` | определяет оператор |
| E | всегда | `REJECTED` | — |

Дополнительные правила:
- `COUNTER_OFFER` создаётся только если итоговая сумма ≥ минимума продукта; иначе `REJECTED` с причиной `INSUFFICIENT_CAPACITY`.
- Если данные ЕГРЮЛ противоречат заявке (`declared_address` или основной ОКВЭД не совпадают) → `NEEDS_INFO` с кодом `REGISTRY_MISMATCH`.
- Отсутствие обязательного документа → `NEEDS_INFO` с кодом `DOCUMENT_MISSING` (на шаге `DATA_CHECK`).
- Недоступность БКИ/ЕГРЮЛ после повторов → `MANUAL_REVIEW` с кодом `SOURCE_UNAVAILABLE`.

## Коды причин (`reason_codes`) и тексты для клиента

| Код | Текст для клиента |
|---|---|
| `REGISTRY_NOT_ACTIVE` | По данным реестра, компания не ведёт деятельность |
| `BKI_OVERDUE_90` | Есть длительная просрочка по действующим обязательствам |
| `NEGATIVE_REVENUE` | Недостаточные показатели деятельности |
| `AGE_TOO_LOW` | Компания работает слишком недолго для этого продукта |
| `LOW_SCORE` | Совокупная оценка заявки ниже требуемой |
| `INSUFFICIENT_CAPACITY` | Платёжеспособность не позволяет одобрить минимальную сумму продукта |
| `DOCUMENT_MISSING` | Необходимо приложить документ |
| `REGISTRY_MISMATCH` | Сведения в заявке отличаются от данных реестра |
| `AMOUNT_REDUCED` | Мы можем предложить меньшую сумму |
| `SOURCE_UNAVAILABLE` | Не удалось получить данные проверки, заявку проверит специалист |
| `INVALID_INN` | ИНН указан неверно, проверьте номер |
| `PRODUCT_NOT_AVAILABLE` | Этот продукт пока недоступен для вашей компании, попробуйте другой |
| `INFO_ROUNDS_EXCEEDED` | Заявку проверит специалист банка |
| `TAKEN` | (служебный, клиенту не показывается) |

## Контракт модуля скоринга

```python
# backend/app/scoring/__init__.py
def score(inputs: ScoringInputs) -> ScoringResult: ...
# ScoringResult: score:int, grade:str, factors:list[FactorLine], knockouts:list[str]

# backend/app/decision/__init__.py
def decide(inputs: ScoringInputs, result: ScoringResult, product: Product) -> Decision: ...
# Decision: outcome in {OFFER, COUNTER_OFFER, MANUAL_REVIEW, NEEDS_INFO, REJECTED},
#           offer: {amount_rub, term_months, rate_percent} | None, reason_codes: list[str]
```
Оба модуля — чистые функции без обращения к БД и сети; их удобно покрыть тестами таблицей (`pytest.mark.parametrize` по тестовым компаниям).

## ИИ (необязательно, за флагом `AI_ENABLED`)
Допустимые применения: простое объяснение решения клиенту (на основе `reason_codes`), краткая сводка заявки для оператора, помощник подбора продукта. Только модели с открытыми весами (рекомендация организаторов: не крупнее 120 млрд параметров). Подключение через клиента, совместимого с OpenAI API (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`): провайдера, ключ и модель можно заменить без правки кода; модель в Docker запускать не обязательно. ИИ не даёт преимущества при оценке сам по себе. Решение о кредите ИИ не принимает. Fallback: шаблонные тексты из таблицы кодов причин.

## Объяснение решения клиенту
Организаторы просили прозрачности: по каким данным получен результат и почему. Оператор видит полный разбор по факторам. Клиент видит краткое объяснение: до двух факторов, которые помогли заявке (наибольшая доля набранных баллов от максимума), и до двух, которые повлияли негативно (наименьшая доля), в виде понятных фраз без внутренних весов и баллов. Для отказа добавляются причины из таблицы кодов. Для передачи в интерфейс в API нужно поле (например, `decision_highlights: string[]` в схеме `Application`); добавляется отдельным PR `contract`.
