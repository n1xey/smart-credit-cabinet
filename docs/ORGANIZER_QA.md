# Ответы организаторов (вебинар) и что из них следует

Источник: документ «Вопросы с вебинара / Умный кредитный кабинет предпринимателя» (52 вопроса). Ниже краткий пересказ тех ответов, которые влияют на решение, и наши выводы. Это часть требований наравне с кейсом.

## Объём и сценарий
| Тема | Ответ организаторов (вопрос) | Вывод для проекта |
|---|---|---|
| Посткредитное обслуживание | Не нужно, сценарий заканчивается выдачей (1) | Последний статус `DISBURSED`, ничего после него не делаем |
| Этапы процесса | Состав и обоснование определяет команда; нужен сквозной путь до решения и моделируемой выдачи (2, 6) | Сквозной путь в приоритете, упрощения явно описываем |
| Завершение демо | Советуют показать принятие предложения и факт выдачи в упрощённом виде (7) | Демо заканчивается экраном выдачи |
| Исходы заявки | Перечень не закреплён; обработка должна быть логичной и объяснимой (8) | Приоритет: оффер, отказ, контр-оффер, ручная проверка; запрос уточнений в конце списка |
| Автоматика и человек | Распределение выбираем сами и обосновываем (10) | Раздел «Кто решает» в `MVP.md` |
| Интересы банка | Решение должно учитывать и клиента, и банк (38) | Показываем долю автоматических решений и время обработки |

## Клиенты и данные
| Тема | Ответ | Вывод |
|---|---|---|
| Регистрация и вход | Регистрация нового юрлица не нужна, рассматривается действующий клиент банка; способ входа выбираем и обосновываем (3, 9) | Вход под учётной записью из seed, обоснование в `MVP.md` |
| Заёмщики | Только действующие клиенты-предприниматели; различия ИП и юрлиц учитываем там, где они влияют (9, 16) | Одна форма профиля, различия только в проверках и данных |
| Поля данных | Обязательного списка нет, каждый параметр должен иметь смысл для процесса (28) | Таблица «Поля данных и зачем» в `MVP.md` |
| Данные | Реальных данных не дадут, используем синтетические (29) | Seed собираем сами |
| Документы | Загрузка и обработка не обязательны (30); анализ счетов по желанию, с объяснением роли в процессе (31) | Загрузка остаётся имитацией, OCR не делаем |

## Интерфейс и дизайн
| Тема | Ответ | Вывод |
|---|---|---|
| Интерфейс сотрудника банка | Обработку банком показать нужно, отдельный интерфейс не обязателен (4, 17) | Оставляем минимальный экран оператора |
| Дизайн-система Альфа-Банка | Использовать можно, но не обязательно; логотип и цвета банка допустимы (15, 18) | Используем `@alfalab/core-components-*` |
| Мобильная версия | Не обязательна, небольшой плюс (14) | Сначала десктоп |
| Подписание | Допустима имитация (код подтверждения), с явной пометкой (12) | Ввод кода в демо, пометка «имитация» |

## Кредитная логика
| Тема | Ответ | Вывод |
|---|---|---|
| Продукты | Можно придумать свои (34) | Три собственных продукта |
| Реалистичность условий | Условия по рыночной логике, с учётом ключевой ставки (35) | Ставка = ключевая + спред + надбавка группы, параметр в конфиге |
| Факторы | Перечень не закреплён, нужно объяснить влияние на решение (36) | Скоринговая карта по факторам |
| Прозрачность | Логика должна быть понятна: по каким данным и почему (37) | Разбор для оператора и краткое объяснение клиенту |
| Моки и упрощения | Допустимы при явном описании; приоритет у проработанной основы (5, 11, 33) | Все допущения в `MVP.md` и README |

## ИИ и модели
| Тема | Ответ | Вывод |
|---|---|---|
| ML и LLM | Не обязательны, преимущества не дают (19, 47) | ИИ делаем последним |
| Доступ к LLM | Сторонний API допустим, но клиент должен быть совместим с OpenAI API с заменой base URL, токена и модели (20, 23) | Клиент с `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` |
| Открытые веса | Требование относится к LLM, OCR и другим моделям; закрытые OCR недопустимы; указывать происхождение (24) | Только открытые модели, источник и лицензия в `THIRD_PARTY_NOTICES.md` |
| Размер модели | Жёсткого лимита нет, рекомендуют не крупнее 120 млрд параметров (21) | Придерживаемся |
| Docker | Модель в Docker класть не нужно, остальное в Docker (39) | Ollama в основной compose не включаем |
| Заглушка вместо ML | Допустима с обоснованием и планом замены (27) | Детерминированный скоринг, описание пути к ML в README |

## Запуск и проверка
| Тема | Ответ | Вывод |
|---|---|---|
| Проверка | Организаторы запустят решение сами по инструкции; видео и демо недостаточно (43) | Запуск одной командой, понятный README |
| Онлайн-демо | Допустимо, но только как дополнение (40, 44) | Облако не заменяет локальную версию |
| Интернет | Во время проверки будет (45) | Запуск всё равно не должен зависеть от внешних сервисов |
| Ресурсы | Ориентиры: около 12 ГБ ОЗУ для серверного запуска, ноутбук с 8 ГБ для клиентской части (41) | Лёгкий стек, следим за размером образов |
| Производительность | Жёстких SLA нет, свои цели оценят положительно (42) | Таблица целевых показателей в `MVP.md` |
| Документация | Нужна отдельная документация: данные, обмен, API, допущения (49); исследования полезны, если повлияли на решение (48) | Диаграмма обмена, допущения и требования в `docs/` |

## Что остаётся неизвестным (уточнить у организаторов)
- Срок сдачи и часовой пояс фиксации версии.
- Формат и длительность защиты.
- Что имелось в виду под «новостной лентой» на слайде 7 кейса: в ответах организаторов её нет, поэтому `/feed` остаётся необязательным.
