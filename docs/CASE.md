# Краткое изложение кейса

**Кейс:** «Умный кредитный кабинет предпринимателя» (Альфа-Банк, Changellenge).
**Вопрос кейса:** как создать цифровой кредитный конвейер для малого и микробизнеса, который ведёт предпринимателя от потребности в финансировании до результата по заявке, а банку позволяет управлять процессом в едином продукте.

## Что нужно сделать
1. Исследовать предметную область и потребности пользователей.
2. Спроектировать модель кредитного процесса: границы, этапы, участники, данные, результаты.
3. Реализовать личный кабинет клиента: выбор продукта, прохождение всех этапов от заявки до результата.
4. Продумать обработку заявки на стороне банка: этапы движения заявки и модель решения.
5. Объединить всё в одну работающую бизнес-логику: данные сохраняются, система реагирует на действия, состояние заявки отображается динамически.

## Целевой пользователь
Владелец, гендиректор, финдиректор/бухгалтер или иной сотрудник, оформляющий заявку от имени компании. Может не обладать банковской экспертизой: интерфейс объясняет варианты, статус и следующие действия.

## Логика процесса из кейса
- Потребность → выбор продукта → заявка (сумма, срок, цель, данные о клиенте и бизнесе).
- Банк: приём, проверка полноты и корректности, при нехватке данных — запрос уточнения.
- Обогащение: бюро кредитных историй, ЕГРЮЛ/ЕГРИП, «Прозрачный бизнес» ФНС (у нас моки).
- **Скоринг ≠ кредитное решение.** Скоринг даёт оценку риска; решение учитывает продукт, сумму, срок, проверки и правила банка. Скоринг может быть правилами или балльной картой, не обязательно ML.
- Исход не бинарный: предложение условий, предложение других условий (сумма/срок/продукт), запрос данных, отказ.
- После одобрения: оформление документов и выдача (разрешено моделировать).

## Ограничения
Комплексность; независимость от платных ресурсов; синтетические данные; автономность (моки вместо интеграций); сценарий только внутри продукта; допустимые упрощения (явно описанная логика решения, подписание и выдача без реальных операций); только веб; LLM только с открытыми весами.

## Обязательные материалы сдачи
GitHub с историей коммитов и однозначным идентификатором версии на дедлайн (доступ для `alfa-hack-2026`, если репозиторий приватный); Docker и единый запуск; lock-файлы; README (назначение, архитектура, окружение, запуск, конфигурация, компоненты, пошаговая проверка); синтетические данные и тестовые учётки; `THIRD_PARTY_NOTICES`; архитектурная схема, описание API, OpenAPI/Swagger, коллекция запросов, диаграмма состояний заявки, модель данных, тестовые сценарии. Публикация на бесплатном сервере желательна.

## Критерии оценки
Целостность; готовность к проверке; качество UX; согласованность модулей; enterprise-ориентированность (безопасность, надёжность, отказоустойчивость, масштабирование, сопровождение); потенциал развития.

## Неясности (уточнить у организаторов)
- Дедлайн и формат защиты.
- На слайде 7 упомянута «новостная лента под клиента», в остальном кейсе её нет. Страховка: блок «Полезное для вас» (`GET /feed`), зависящий от статуса заявки и типа бизнеса.
