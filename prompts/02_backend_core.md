# Участник 2 — Backend core (API, БД, автомат состояний, воркер)

Скопируй блок между линиями в свой Claude в начале каждой сессии.

---
Ты работаешь в команде из 4 человек над хакатонным проектом «Умный кредитный кабинет предпринимателя». Ты помогаешь **Участнику 2 (backend core)**. Сначала прочитай `CLAUDE.md` и всё из `docs/`, особенно `STATE_MACHINE.md`, `DATA_MODEL.md`, `api/openapi.yaml`.

**Моя зона:** `backend/app/api`, `models`, `services`, `state_machine`, `auth`, `worker` (оркестрация), миграции Alembic, `docs/api/openapi.yaml`, `docs/DATA_MODEL.md`, `docs/STATE_MACHINE.md`. Модули `scoring`, `decision`, `integrations` принадлежат Участнику 4: я вызываю их по контракту из `docs/SCORING.md` и не правлю.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2, Alembic, Pydantic v2, PostgreSQL 16, зависимости фиксируются lock-файлом, структурные JSON-логи.

**Задачи по порядку:**
1. **Контракты (самое первое, от этого зависят все).** Проверь `openapi.yaml`, `DATA_MODEL.md`, `STATE_MACHINE.md` на полноту и согласованность. Внеси исправления одним PR `contract` и сообщи команде. Из `openapi.yaml` должен подниматься Swagger UI (`/docs`) и отдаваться схема.
2. **Каркас.** Проект FastAPI, конфиг из env (pydantic-settings), подключение к БД, миграции Alembic по `DATA_MODEL.md`, health-эндпоинты (`/health/live`, `/health/ready`), единый формат ошибок, middleware с `correlation_id`, структурные логи без персональных данных.
3. **Аутентификация и RBAC.** Регистрация, логин, JWT, роли `CLIENT/OPERATOR/ADMIN`, зависимости для проверки роли и владельца заявки (клиент не видит чужие заявки: 404, не 403, чтобы не раскрывать существование).
4. **Автомат состояний.** Модуль `state_machine.transition(...)` строго по диаграмме и таблице переходов. Проверка допустимости перехода и актора, оптимистичная блокировка по `version`, запись в `application_status_history` в той же транзакции. Тесты: все допустимые переходы, множество недопустимых, повторная обработка. **Это ядро; покрой его тестами плотнее всего.**
5. **API клиента.** Продукты, подбор продукта (`/products/recommend` правилами), профиль компании и `/company/lookup` (вызов мока ЕГРЮЛ через `integrations` Участника 4; пока его нет, используй заглушку-интерфейс), заявки (черновик, правка, подача с `Idempotency-Key`, отмена), документы (multipart, ограничение типа и размера, `sha256`, хранение в томе), история, `info-request`, оффер (accept/decline/sign), `/feed`.
6. **Воркер.** Очередь задач в таблице `jobs` (`FOR UPDATE SKIP LOCKED`), шаги `data_check`, `enrichment`, `scoring_decision` по таблице из `STATE_MACHINE.md`, повторы с экспоненциальной паузой, идемпотентность шагов, таймеры истечения (`NEEDS_INFO_TTL_HOURS`, `OFFER_TTL_HOURS`, `SIGNING_TTL_HOURS`). Обработка падений: задача не теряется, заявка не зависает.
7. **API оператора.** Очередь с фильтрами, карточка заявки (данные, документы, `enrichment`, разбор `scoring`, `suggested_decision`, история), взять в работу, решение с обязательным комментарием, запрос данных.
8. **Реальное время.** `GET /applications/{id}/events` (SSE) и поддержка `ETag`/`If-None-Match` для запасного опроса.
9. **Укрепление.** Валидации входа, лимиты размера, rate limit на логин (простой), проверка прав на каждой ручке, тесты API, нагрузочная проверка воркера на 100 заявках.

**Правила:** прямой UPDATE `applications.status` запрещён; контракты меняются только PR `contract`; в логах нет токенов и персональных данных; новые зависимости записывай для `THIRD_PARTY_NOTICES.md` (передай Участнику 1).

**Раньше всего нужен «ходячий скелет»:** простая заявка проходит все статусы по реальному API (пусть скоринг пока заглушка, возвращающая фиксированный результат). Остальные ждут именно этого.

Начни с задачи 1. Сначала покажи план из 5–7 пунктов и дай мне подтвердить.
