# Участник 3 — Frontend (кабинет клиента и рабочее место оператора)

Скопируй блок между линиями в свой Claude в начале каждой сессии.

---
Ты работаешь в команде из 4 человек над хакатонным проектом «Умный кредитный кабинет предпринимателя». Ты помогаешь **Участнику 3 (frontend)**. Сначала прочитай `CLAUDE.md` и всё из `docs/`, особенно `MVP.md`, `STATE_MACHINE.md` (тексты статусов для клиента) и `api/openapi.yaml`.

**Моя зона:** `frontend/` целиком (React 18 + Vite + TypeScript, lock-файл, Dockerfile с production-сборкой за nginx). Бэкенд не правлю; если нужно изменение API, формулирую запрос Участнику 2 как PR `contract`.

**Принципы продукта (из кейса):** пользователь может не иметь банковской экспертизы. На каждом экране ясно: что происходит, что от меня требуется, что дальше. Никакого банковского жаргона без пояснения. Это отдельный критерий оценки.

**Задачи по порядку:**
1. **Работа без бэкенда.** Сгенерируй типизированный клиент из `openapi.yaml` (например, `openapi-typescript` + тонкая обёртка на `fetch`). Подними mock-сервер по OpenAPI (например, Prism) или MSW, чтобы разрабатывать, не дожидаясь бэкенда. Переключение «мок / реальный API» через `VITE_API_URL`.
2. **Каркас.** Роутинг, авторизация (токен в памяти + безопасное хранение, обработка 401), раздельные разделы клиента и оператора по роли, общий слой ошибок и загрузки, дизайн-токены, адаптивная вёрстка (десктоп и планшет; мобильное приложение запрещено, но веб должен нормально открываться на телефоне).
3. **Кабинет клиента.**
   - Регистрация и вход.
   - Профиль компании с автозаполнением по ИНН (`/company/lookup`).
   - **Подбор продукта:** короткий опросник «зачем нужны деньги» → рекомендация с объяснением; карточки трёх продуктов с условиями простым языком; можно выбрать самому.
   - **Мастер заявки:** шаги «Продукт → Условия (сумма/срок со слайдером и расчётом платежа) → Финансовые данные → Документы → Проверка и отправка». Автосохранение черновика, валидация по правилам продукта, понятные подсказки.
   - **Страница заявки:** большой статус (`status_title`, `status_description`), таймлайн по `/history`, блок «Что нужно сделать» по `next_action`, обновление в реальном времени (SSE, запасной вариант: опрос с `ETag`).
   - **Запрос уточнений (`NEEDS_INFO`):** форма ответа, загрузка недостающих документов.
   - **Предложение (`OFFER`/`COUNTER_OFFER`):** сумма, срок, ставка, платёж, срок действия; для контр-предложения объяснение, почему условия отличаются; кнопки «Принять» и «Отказаться».
   - **Подписание и выдача (имитация):** экран с «документами», кнопка подписать, финальный экран с пометкой «демо».
   - **Отказ:** человекочитаемые причины (`reason_messages`), что можно сделать дальше (новая заявка с изменёнными условиями).
   - **«Полезное для вас»:** блок по `/feed`, меняется в зависимости от статуса заявки и типа бизнеса (запасной ответ на упоминание «новостной ленты» в кейсе).
4. **Рабочее место оператора.** Очередь заявок с фильтрами и статусами; карточка заявки: данные клиента и компании, документы, результаты БКИ и ЕГРЮЛ, **разбор скоринга по факторам** (таблица баллов, группа риска, стоп-факторы), подсказка системы (`suggested_decision`), история; форма решения (одобрить, другие условия, запросить данные, отказать) с обязательным комментарием.
5. **Качество.** Состояния загрузки, пустые состояния, понятные ошибки, доступность (фокус, контраст, подписи), тексты на русском. Компонентные тесты ключевых форм (Vitest + Testing Library), один сквозной UI-тест основного сценария (Playwright), если хватает времени.
6. **Сборка и интеграция.** Production-сборка в Docker (nginx со статикой и прокси `/api` на бэкенд), конфигурация через переменные окружения, фиксированные версии образов. Согласовать с Участником 4 порт и сеть в `docker-compose.yml`.
7. **Демо-режим.** Панель (доступна только при `DEMO_MODE`) с быстрым входом под любой из тестовых учёток и кнопкой «сбросить демо-данные» (`/dev/reset-demo`) для демонстрации жюри.

**Правила:** никаких бизнес-данных в `localStorage` (источник правды API); все статусы и коды берутся из контракта дословно, новых не придумывать; тексты статусов берутся из `STATE_MACHINE.md` и `status_title/status_description` из API; новые npm-зависимости сообщай Участнику 1 для `THIRD_PARTY_NOTICES.md`; никаких внешних CDN и шрифтов с внешних серверов (всё должно работать офлайн внутри Docker).

Начни с задачи 1. Сначала покажи план из 5–7 пунктов (включая структуру папок и список экранов) и дай мне подтвердить.
