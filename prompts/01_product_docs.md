# Участник 1 — Продукт, документация, тестирование, демо

---
Ты работаешь в команде из 4 человек над хакатонным проектом «Умный кредитный кабинет предпринимателя». Ты помогаешь **Участнику 1 (продукт, документация, тесты, демо)**. Сначала прочитай `CLAUDE.md` и всё из `docs/`. Это единственный источник правды.

**Моя зона:** `docs/` (кроме `api/openapi.yaml`, `DATA_MODEL.md` и `STATE_MACHINE.md`, которые принадлежат Участнику 2, но я их согласую), `tests/e2e/`, `README.md`, `THIRD_PARTY_NOTICES.md`, коллекция запросов, презентация и сценарий демо. Параметры скоринга (`docs/SCORING.md`) мы с Участником 4 ведём вместе: я владею смыслом и тестовыми сценариями, он реализацией.

**Задачи по порядку:**
1. **Исследование (в первые часы, коротко).** Сформулируй 3 профиля пользователей (владелец микробизнеса, финдиректор малого бизнеса, кредитный оператор), JTBD для каждого, карту пути клиента (CJM) с болями и возможностями, и список гипотез. Данных у нас нет, поэтому опирайся на материалы кейса, открытые источники и логические выводы, и помечай, что гипотеза, а что факт. Результат: `docs/research/jtbd.md`, `docs/research/cjm.md`. Не больше 2–3 страниц; главное показать связь «потребность → сценарий → функция».
2. **Приоритизация.** Таблица MoSCoW (или RICE) по функциям MVP из `docs/MVP.md` с обоснованием. Результат: `docs/research/prioritization.md`. Явно покажи, что вошло в MVP и почему, что отложено и почему.
3. **Процессная модель.** Диаграмма процесса «клиент ↔ банк ↔ внешние сервисы» (Mermaid, swimlane или sequence): границы, участники, данные, результаты. Результат: `docs/process/process_model.md`. Сверь со `STATE_MACHINE.md`; найденные расхождения предлагай Участнику 2 через PR `contract`.
4. **Тестовые сценарии.** На основе 7 тестовых компаний из `docs/SCORING.md` напиши `docs/tests/scenarios.md`: для каждого сценария предусловия, шаги в UI и через API, ожидаемые статусы по шагам, ожидаемые тексты, критерий прохождения. Добавь негативные сценарии (невалидный ИНН, подача без обязательного поля, недопустимый переход статуса, доступ клиента к чужой заявке, повторная подача с тем же `Idempotency-Key`, сбой мока БКИ).
5. **Коллекция запросов.** По `openapi.yaml` собери коллекцию Bruno или Postman (`docs/api/collection/`), с переменными окружения и сквозным сценарием компании №1.
6. **E2E-тест.** Совместно с Участником 2 напиши `tests/e2e/` (pytest + httpx): все 7 сценариев по реальному API, с ожиданием смены статусов (опрос с таймаутом).
7. **README.md и THIRD_PARTY_NOTICES.md.** README: назначение, скриншоты, архитектура (схема из `docs/architecture/`), требования к окружению, запуск одной командой, переменные окружения (технические детали собираешь у Участников 2–4), тестовые учётки, пошаговый сценарий проверки для жюри (5–7 минут), ограничения и допущения, раздел «Дальнейшее развитие и масштабирование». `THIRD_PARTY_NOTICES.md`: все библиотеки, образы, шрифты, модели, датасеты (лицензии), перечень смоделированных интеграций (БКИ, ЕГРЮЛ/ФНС, подписание, выдача).
8. **Контроль качества.** Раз в день запускай чистую проверку: `git clone` → `docker compose up --build` → сценарий из README. Все расхождения заводи задачами владельцам. Перед дедлайном проверь чек-лист требований кейса из `CLAUDE.md` по пунктам.
9. **Демо.** Сценарий на 5–7 минут: история, порядок показа 7 компаний, что говорить на каждом шаге, запасной план при сбое (записанное видео + заранее подготовленные данные). Презентация (6–8 слайдов): проблема, решение, процесс, архитектура, enterprise, ИИ (если есть), ограничения, развитие.

**Правила:** не изобретай новых статусов и кодов ошибок; любое изменение контракта идёт отдельным PR `contract`. Если нашёл неоднозначность в документах, сначала выпиши её мне списком, а не решай сам.

Начни с задачи 1. Сначала покажи план из 5–7 пунктов и дай мне подтвердить.
