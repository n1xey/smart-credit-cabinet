# CLAUDE.md — контекст проекта для всех участников и всех Claude

Проект: **Умный кредитный кабинет предпринимателя** (хакатон «Альфа Будущее»).
Цель: работающий прототип цифрового кредитного конвейера для малого и микробизнеса.
Клиент выбирает продукт и подаёт заявку в кабинете, банк обрабатывает её в том же продукте,
статус заявки меняется последовательно и виден клиенту в реальном времени.

**Перед любой работой прочитай:** `docs/CASE.md`, `docs/ORGANIZER_QA.md`, `docs/MVP.md`, `docs/STATE_MACHINE.md`,
`docs/SCORING.md`, `docs/DATA_MODEL.md`, `docs/api/openapi.yaml`. Это единственный источник правды.

## Жёсткие ограничения (нарушать нельзя)
1. Запуск одной командой: `docker compose up --build` на обычном ПК. Без ручных шагов.
2. Никаких платных API, подписок, покупных данных, корпоративных систем. Внешние сервисы (БКИ, ЕГРЮЛ/ФНС) только моки в отдельных контейнерах.
3. Только синтетические данные. Реальных ИНН, ФИО, паспортов не использовать (наши ИНН начинаются с `00`).
4. Весь сценарий внутри продукта: никаких email, SMS, мессенджеров, звонков (даже как «заглушка в потоке»).
5. Только веб-интерфейс.
6. LLM и другие модели (в том числе OCR) только с открытыми весами; рекомендация организаторов: не крупнее 120 млрд параметров. Только за флагом `AI_ENABLED`, через клиента, совместимого с OpenAI API: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` задаются переменными окружения, провайдера можно сменить без правки кода. Обязателен детерминированный fallback: без флага продукт полностью работает. Платные сторонние API по умолчанию не используем (допустимы только как заменяемый провайдер, см. `docs/ORGANIZER_QA.md`). Модель в Docker класть не обязательно.
9. Ответы организаторов вебинара (`docs/ORGANIZER_QA.md`) — часть требований наравне с кейсом: приоритеты и границы MVP определяются в том числе ими.
7. Версии зафиксированы: lock-файлы, теги Docker-образов без `latest`.
8. Всё, что используем из сторонних компонентов, записывается в `THIRD_PARTY_NOTICES.md`.

## Стек (менять только по решению всей команды)
- Backend: Python 3.12, FastAPI, SQLAlchemy 2 + Alembic, Pydantic v2, PostgreSQL 16. Зависимости через `uv`/`pip-tools` с lock-файлом.
- Worker: отдельный процесс на том же коде, очередь в PostgreSQL (`SELECT ... FOR UPDATE SKIP LOCKED`). Без Redis/Kafka в MVP; в README описать как масштабировать.
- Frontend: React 18 + Vite + TypeScript, `package-lock.json`. Клиент API генерируется из `openapi.yaml`.
- UI: дизайн-система Альфа-Банка `@alfalab/core-components-*` (лицензия MIT, точные версии в `package.json`). Новые компоненты берём только из неё, другие UI-библиотеки не добавляем; логотип и фирменные цвета банка использовать можно. Приоритет: качественный десктоп; мобильная адаптация вторична.
- Моки: `mocks/bki`, `mocks/egrul` — отдельные FastAPI-контейнеры.
- Тесты: pytest (backend), Vitest (frontend), e2e сценарий в `tests/e2e` (pytest + httpx по API).

## Структура репозитория и владельцы
```
backend/app/api, models, services, state_machine, auth   -> Участник 2
backend/app/scoring, decision, integrations              -> Участник 4
backend/app/worker                                       -> Участник 2 (оркестрация), 4 (шаги scoring/decision)
frontend/                                                -> Участник 3
mocks/ seed/ docker-compose.yml Makefile .github/        -> Участник 4
docs/ tests/e2e README.md THIRD_PARTY_NOTICES.md         -> Участник 1
```
Правило: **один модуль — один владелец**. Чужие файлы правятся только через PR и согласование.

## Работа с контрактами
- Контракты: `docs/api/openapi.yaml`, `docs/STATE_MACHINE.md`, `docs/DATA_MODEL.md`, `docs/SCORING.md`.
- Контракт меняется **только отдельным PR** с пометкой `contract`. После merge все подтягивают изменения.
- Статусы заявки и коды ошибок берутся из контракта дословно, новых не изобретать.
- Все переходы статусов идут через единый `state_machine.transition(...)`, прямой UPDATE поля `status` запрещён. Каждый переход пишет строку в `application_status_history`.

## Соглашения
- Деньги: целые рубли (`integer`), поля называются `*_rub` (например `amount_rub`). Проценты — число, например `18.5`.
- Время: UTC ISO-8601. Идентификаторы: UUID.
- Ошибки API: `{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [...] } }`.
- В логах нет персональных данных и токенов; структурные JSON-логи с `application_id` и `correlation_id`.
- Секреты только через переменные окружения; все переменные описаны в `.env.example`.
- Каждая новая функция идёт с тестом. Особенно: автомат состояний, скоринг, матрица решений.
- Коммиты небольшие, сообщения вида `feat(scoring): ...`, `fix(api): ...`, `docs: ...`.
- Ветки `feat/<модуль>-<суть>`, merge в `main` только через PR, рецензент — Claude или человек другого участника.

## Definition of Done для любой задачи
Код + тест проходят, `docker compose up --build` по-прежнему поднимается с нуля, контракт и документация обновлены, нет новых зависимостей без записи в `THIRD_PARTY_NOTICES.md`.

## Чего не делать
- Не добавлять функции вне MVP (`docs/MVP.md`, раздел «Не входит»), пока не работает основной сценарий.
- Не использовать `localStorage` для бизнес-данных: источник правды — API/БД.
- Не хардкодить исход заявки в коде: он следует из данных, скоринга и матрицы решений.
- Не развивать, пока не работает основной сценарий: посткредитное обслуживание, регистрацию новых компаний (рассматриваем действующих клиентов банка), распознавание документов (OCR), мобильную версию, блок «Полезное для вас».
- Не делать коммитов после дедлайна и не менять тег релиза.
